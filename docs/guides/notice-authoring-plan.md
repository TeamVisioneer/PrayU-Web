# 공지 저작·게시 계획

릴리스마다 반복될 작업이므로 **절차를 고정**한다. 그때그때 판단하면 세션과 함께 휘발된다.

## 결정 (2026-07-28)

| 항목 | 결정 | 이유 |
|---|---|---|
| 저작 위치 | **레포에 원고를 커밋**하고 PR에서 리뷰 | 공지 문구가 git에 남아야 "그때 뭐라고 공지했지"를 추적할 수 있다 |
| 게시 경로 | **어드민 UI** (마이그레이션 아님) | 공지를 DB로 옮긴 이유가 "문구 수정·중단에 배포가 필요했다"(#403 핫픽스)인데, 마이그레이션 게시는 그 이점을 반납한다 |
| 이미지 | **기본은 레포 `public/images/notice/`**, 어드민에서 즉석 작성하는 공지만 Storage 업로드 | 원고와 짝을 이루는 이미지는 PR에서 함께 리뷰되고 환경에 무관해야 한다 |
| 어드민 보조 | **레포 원고 목록에서 초안 등록** (2026-07-28 개정) | 손으로 옮겨 적는 단계를 없앤다 — 아래 "게시 방식 개정" 참조 |

## 이미지 — 레포가 기본, Storage는 예외

| 경우 | 위치 | 원고의 `images` |
|---|---|---|
| **릴리스 공지**(원고를 레포에 두는 경우) | `public/images/notice/<slug>/*.png` | `/images/notice/<slug>/1.png` 처럼 **상대경로를 원고에 함께 적는다** |
| **즉석 공지**(어드민에서 바로 작성) | 어드민 업로드 → Storage `prayu/notice/` | 원고 없음 |

레포 경로를 기본으로 두는 이유는 **환경 종속** 때문이다. 어드민 업로드는
`https://<프로젝트 ref>.supabase.co/storage/v1/object/public/prayu/notice/...` 형태의 절대 URL을 만들어,
staging에서 만든 URL을 prod 공지에 넣으면 **prod 화면이 staging 버킷을 가리킨다.**
상대경로는 그 문제가 없고, 스크린샷이 PR diff에 남아 리뷰된다.

`<img src>`에 값을 그대로 넣으므로 두 형태 모두 동작한다(레거시 공지 이미지 7개가 이미 상대경로다).
어드민에는 **URL 직접 입력**을 추가해 레포 경로를 넣을 수 있게 한다 — 이게 기본 입력 수단이 되고,
업로드 버튼은 즉석 공지용으로 남는다.

**대신 이미지가 바뀔 때는 web 배포가 필요하다.** 문구 수정은 여전히 배포 없이 되고,
급하게 이미지만 갈아야 하면 그때는 Storage 업로드로 덮으면 된다.

## 원고 형식 — 프론트매터 마크다운

```markdown
---
title: 말씀카드가 더 편해졌어요
target: all
starts_at: 2026-08-01 09:00
ends_at:
cta_label: 말씀카드 만들러 가기
cta_url: /bible-card/new
images:
  - /images/notice/2026-08-01-bible-card/1.png
  - /images/notice/2026-08-01-bible-card/2.png
---

**공유하면 생성 횟수가 늘어나요**

- 카카오톡으로 말씀카드를 공유하면 그날 만들 수 있는 횟수가 늘어납니다
```

- **JSON이 아니라 프론트매터를 쓰는 이유**: 본문이 JSON 문자열이 되면 PR diff가 `\n` 투성이가 되어
  정작 리뷰해야 할 **문구**가 안 읽힌다. 붙여넣기 가져오기는 JSON도 받아들이되(`{`로 시작하면 JSON으로 파싱),
  레포 원고는 마크다운으로 둔다
- 프론트매터 키는 **스칼라 문자열 + `images` 목록**까지만 허용한다. 그 이상 중첩이 필요해지면 그때 다시 논의한다 (직접 만든 파서를 키우지 않는다)
- `images`가 있으면 붙여넣기 가져오기가 폼의 이미지 목록을 **그 값으로 교체**한다. 키가 없으면 이미 올린 이미지를 유지한다
- 본문에서 쓸 수 있는 문법은 렌더러가 지원하는 **`**굵게**` · `- 목록` · 빈 줄 문단**이 전부다
  ([noticeMarkdown.tsx](../../src/components/notice/noticeMarkdown.tsx))

## 게시 방식 개정 (2026-07-28)

처음에는 **원고를 어드민에 붙여넣는** 방식이었다. 실제로 써 보니 두 가지가 걸렸다.

- 같은 원고를 staging·prod 에 **각각 손으로** 옮겨야 한다 — 언젠가 어긋난다
- 붙여넣기 자체가 실패하기도 했다(렌더된 마크다운에서 복사하면 코드펜스가 딸려 온다)

**마이그레이션으로 넣는 안도 검토했다가 접었다.** 자동 전파는 매력적이지만
공지 문구는 서비스 데이터이지 스키마가 아니라서, 마이그레이션 히스토리에 남길 성격이 아니다.

### 지금 방식 — 어드민이 레포 원고를 읽어 초안으로 등록한다

```
운영 탭 → 공지 관리
  ├ 레포 원고
  │   2026-07-28-bible-card-update   [미등록]  → 초안으로 등록
  │   2026-08-15-thanks-card         [등록됨]
  └ 등록된 공지
      말씀카드가 더 편해졌어요  [초안]  → 미리보기 → 노출
```

- 원고는 `import.meta.glob` 으로 **번들에 실려 배포**된다. lazy 라 목록만 들고, 본문은 누를 때 받아온다
- "초안으로 등록"은 `is_active = false` 행을 만든다. 사용자에게는 보이지 않는다
- **등록 순간 원고 내용이 DB 로 복사된다.** 이후 원고 파일을 고쳐도 등록된 공지는 바뀌지 않는다 —
  문구를 고치려면 어드민에서 고치거나, 등록을 지우고 다시 등록한다
- **이미지는 복사되지 않고 경로만 저장된다**(`/images/notice/...`). 이미지 파일을 바꿔 배포하면
  이미 게시된 공지의 이미지도 함께 바뀐다. 텍스트와 이미지의 성격이 다르다는 점을 기억할 것
- `notice.slug` 가 원고와 등록된 공지를 잇는다 (PrayU-Api). 즉석 공지는 slug 가 없다

**원고 붙여넣기 UI 는 제거했다** — 레포 원고 목록이 그 자리를 대신하고, 즉석 공지는 폼에 직접 쓰면 된다.

## 릴리스마다 반복할 절차

1. **원고 작성** — `docs/notices/<yyyy-mm-dd>-<slug>.md`. 릴리스에 포함된 **사용자 대면** 변경만 추린다(내부 개편·리팩터링 제외)
   - ⚠️ **원고 파일에는 공지 내용만 둔다.** 어드민이 파일을 통째로 받아 프론트매터 뒤 전부를 본문으로 읽으므로,
     캡처 목록·게시 기록 같은 부가 정보는 **`<같은이름>.notes.md`** 에 적는다
2. **캡처 목록 확정** — notes 파일에 화면·상태를 적는다
3. **캡처** — `public/images/notice/<slug>/`에 넣는다. 로그인이 필요한 화면은 **로컬 개발 계정**으로 찍을 수 있다 ([dev-seed-plan](../../../PrayU-Api/docs/guides/dev-seed-plan.md))
4. **PR 리뷰** — 원고 + 이미지가 함께 diff에 남는다. 피처 PR과 같이 내도 되고 따로 내도 된다
5. **staging 게시(리허설)** — main merge 로 원고가 staging 에 배포된 뒤, 어드민 → 레포 원고 → **초안으로 등록** → 미리보기 → **노출**
6. **prod 게시** — release 로 원고가 prod 에 배포된 뒤 같은 절차(등록 → 노출). `starts_at`을 미래로 두면 예약 게시가 된다
7. **게시 기록** — notes 파일의 체크박스에 게시일과 환경을 남긴다

## 스크린샷 규격

| 항목 | 기준 |
|---|---|
| 폭 | 모바일 375pt 기준 캡처(실기기 2x/3x 그대로도 무방). 모달 폭에 맞춰 축소되므로 **세로로 긴 전체 화면 캡처는 피한다** |
| 형식 | 정지 화면은 `png`, 동작 설명이 필요하면 `gif` |
| 용량 | 장당 500KB 이하 권장 (모달에서 여러 장을 연속 로드한다) |
| 경로·파일명 | `public/images/notice/<slug>/<n>.png` (즉석 공지의 Storage 업로드는 `notice/<타임스탬프>-<파일명>`) |
| 장수 | 2~4장. 그 이상이면 공지 하나에 너무 많은 걸 담고 있다는 신호 |

## 구현 — 파일 매니페스트

### 신규

| 파일 | 내용 |
|---|---|
| `src/lib/noticeDraft.ts` | 붙여넣은 원고 → 폼 값 파싱. `parseNoticeDraft(raw): { draft, warnings }`. `{`로 시작하면 `JSON.parse`, `---`로 시작하면 프론트매터(첫 `---`~다음 `---` 사이를 `key: value`로 스캔, 나머지 전체가 body). 알 수 없는 키·빈 제목은 `warnings`로 돌려주고 **무시하지 않는다**. UI 없는 순수 함수라 단독으로 검증 가능 |
| `docs/notices/2026-07-28-<slug>.md` | 첫 공지 원고 (아래 초안) |

### 수정

| 파일 | 변경 지점 |
|---|---|
| `src/pages/AdminPage/NoticeManager.tsx` | ① 이미지 섹션에 **URL 직접 입력** 필드 + 추가 버튼 — 레포 경로(`/images/notice/...`)를 넣는 **기본 수단**이 된다. 기존 업로드 버튼은 즉석 공지용으로 남긴다 ② 에디터 헤더에 **원고 붙여넣기** 버튼 → textarea 다이얼로그 → `parseNoticeDraft` → 폼 채움. `images` 키가 있으면 교체, 없으면 기존 유지. 경고는 다이얼로그 안에 표시 ③ 날짜 문자열은 기존 `toLocalInputValue()`로 변환 |
| `docs/backlog.md` | 공지 저작 절차 항목 + 이 문서 링크 |

**새 추상화를 만들지 않는 지점**: 원고를 읽어 자동 게시하는 스크립트/함수는 만들지 않는다.
게시는 사람이 어드민에서 확인하고 누르는 편이 안전하고, 자동화할 만큼 자주 일어나지 않는다.

## 순서 제약 — prod에는 아직 `notice` 테이블이 없다

prod 조회 시 `42P01 relation "public.notice" does not exist`. 어드민 개편분이 **prod release 전**이기 때문이다.

1. prod release (web 먼저 → Api — 성경 동기화 짝 때문)
2. prod 관리자 계정에 `is_admin = true` (안 하면 `/admin` 진입 불가)
3. 그다음에야 prod 공지 게시 가능

## 첫 공지 초안

이번 릴리스의 사용자 대면 변경은 다섯 가지다. 내부 개편(어드민 #471, 토큰화 #465, 백로그 문서)은 제외한다.

| 변경 | PR |
|---|---|
| 카카오톡 공유하면 말씀카드 생성 횟수 추가 | #463 · Api#38 |
| 말씀카드 남은 횟수·매칭 방식 안내, 히스토리에서 공유·카드 뒤집기 | #466 · #467 · #468 |
| 공지사항 목록 페이지 신설 (카카오 채널 링크 대체) | #473 · #469 |
| 성경 본문 정확도 — 잘려 있던 구절 복구, 조회되지 않던 절 추가 | Api#44 · #475 |
| iOS Safari 하단 흰 띠 등 화면 잘림 개선 | #464 |

공지 하나에 다섯을 다 넣으면 읽히지 않는다. **2~3개로 추리는 편**을 권한다 —
공유 보상과 말씀카드 안내는 사용자 행동을 바꾸는 변경이라 넣고, 성경 본문·화면 개선은 "이런 것도 고쳤어요" 한 줄로 묶는다.

문구 초안은 방향 확정 후 `docs/notices/`에 작성한다.
