# 프로필 · 검색 · 팔로우

상위: [overview.md](overview.md) · 상태: **설계 전, 방향만 합의**

## 목표

인스타그램처럼 — 각자의 프로필이 **검색되고**, 서로 **팔로우/팔로잉** 한다.
이게 [피드](feed.md)에 흐를 관계 그래프의 원천이다.

## 지금 있는 것

| 자산 | 상태 |
|---|---|
| `profiles.username` | **컬럼은 있는데 실질적으로 안 쓴다.** SNS 핸들로 승격할 자리 |
| `profiles.full_name`·`avatar_url` | 표시용으로 이미 쓰임 |
| `profiles.blocking_users` (uuid[]) | 차단 기능이 이미 있다 — 팔로우 정책과 맞물린다 |
| 어드민 프로필 검색 | `full_name` like 검색. 사용자 검색의 참고 구현 |
| `deleted_at` (신규) | 탈퇴자를 검색·팔로우에서 제외해야 한다 |

## 필요한 것

### 1) 핸들(`username`) 을 실제로 쓰기

지금은 비어 있거나 임의 값이다. SNS 핸들이 되려면:

- **유일성** — unique 인덱스. 대소문자·유사문자 처리 필요
- **채우기** — 기존 사용자 전원이 `username` 이 없다. 마이그레이션으로 자동 생성할지,
  첫 진입 시 사용자가 정하게 할지 결정 필요
- **변경 정책** — 몇 번까지 바꿀 수 있나. 놓아준 핸들을 남이 주울 수 있나(사칭 위험)
- **금칙어** — 관리자 사칭(`prayu`, `admin`), 욕설

### 2) 팔로우 관계 테이블

```
follow (follower_id, following_id, created_at, ...)
```

결정이 필요한 것:

| 쟁점 | 선택지 |
|---|---|
| **승인제 여부** | 즉시 팔로우 / 비공개 계정 승인제. 기도 앱 특성상 **승인제 수요가 있을 것** |
| 차단과의 관계 | 차단하면 기존 팔로우가 끊기나? `blocking_users` 와 정합성 필요 |
| 카운트 | 팔로워/팔로잉 수를 집계할지 컬럼으로 둘지 (성능) |
| 탈퇴자 | `deleted_at` 인 프로필은 관계에서 제외 |

### 3) 프로필 화면

- 내 프로필 / 남의 프로필 (같은 화면 다른 상태)
- 무엇을 보여주나 — 작성한 게시물? 감사카드? **기도카드는 민감정보라 기본 노출 대상이 아니다**
- 팔로워·팔로잉 목록 화면

### 4) 사용자 검색

- 핸들·이름으로 검색. 인덱스 필요(현재 `like '%...%'` 는 인덱스를 못 탄다)
- 탈퇴자·차단한 사람 제외

## 🔴 프라이버시 — 이 문서에서 가장 중요한 부분

**지금 모든 테이블의 SELECT 가 `using(true)` 다.** 프로필도 마찬가지라,
사실상 이미 전체 공개다(사용자는 모른다). 검색 기능을 만드는 순간 그게 **드러난다.**

- 사용자가 **검색되지 않기를 선택**할 수 있어야 하나? (비공개 계정)
- 기존 사용자는 어떤 기본값으로 시작하나 — **검색 노출 기본 OFF 가 안전하다.**
  어느 날 갑자기 내 이름이 검색되는 것은 사용자 입장에서 사고다
- 카카오 프로필 이름이 실명인 사용자가 많다 (`full_name` 이 카카오에서 온다)

**이건 RLS 정비(security-backlog 1번)와 같은 작업이다** — [overview.md](overview.md) 참조.
