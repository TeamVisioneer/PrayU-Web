# 기독교 SNS 전환 — 전체 그림

> 상태: **방향 수립 단계.** 결정이 필요한 것이 많다 — 6절 참조.
> 하위 문서: [navigation.md](navigation.md) · [profile-social.md](profile-social.md) · [feed.md](feed.md)

## 무엇을 바꾸려는 것인가

지금 PrayU 는 **닫힌 그룹 안에서** 기도제목을 나누는 앱이다.
바꾸려는 것은 **열린 소셜 그래프를 가진 기독교 SNS** 다 — 프로필이 검색되고, 서로 팔로우하고,
피드에서 팔로잉·공개 게시물·그룹 소식을 함께 본다.

이건 피처 추가가 아니라 **제품 정체성의 확장**이다. 그래서 세 가지가 동시에 필요하다.

| 축 | 문서 | 없으면 |
|---|---|---|
| 이동 | [하단 네비게이션](navigation.md) | 화면이 늘어도 갈 길이 없다 |
| 관계 | [프로필·팔로우](profile-social.md) | 피드에 채울 게 없다 |
| 소비 | [피드](feed.md) | 관계를 만들 이유가 없다 |

## 지금 구조에서 가져갈 수 있는 것

| 있는 것 | 쓸모 |
|---|---|
| `profiles.username` 컬럼 | **이미 있는데 안 쓴다.** SNS 핸들(`@handle`)로 승격 가능 |
| `notification` 테이블 | 팔로우·좋아요 알림을 얹을 자리 (`type`·`data` jsonb 존재) |
| `pray_card` · `thanks_card` · `bible_card` | 피드에 흐를 콘텐츠가 이미 3종 있다 |
| R2 업로드 · 이미지 리사이즈 | 게시물 이미지 인프라 완비 |
| 어드민 프로필 검색 | 사용자 검색의 참고 구현 |

## 🔴 가장 큰 걸림돌 — 공개/비공개 개념이 **아예 없다**

현재 스키마에 `is_public`·`visibility` 류 컬럼이 **하나도 없다.**
게다가 모든 테이블의 SELECT 정책이 `using(true)` 라 **로그인만 하면 남의 그룹 기도제목이 다 보인다**
(security-backlog 1번 — 알려진 구멍).

즉 지금은 "공개"가 기본이 아니라 **격리가 없는 상태**다. 여기에 피드를 얹으면
"공개 게시물"과 "원래 안 보여야 했던 글"이 구분되지 않는다.

**기도제목은 민감정보다.** 누군가의 투병·가정사·죄의 고백이 담긴다.
그룹에만 쓴 글이 피드로 새어 나가는 사고는 **되돌릴 수 없다.**

### 그래서 순서가 뒤집힌다

원래 계획은 "RLS 정비(security-backlog 1번)는 릴리스 직후" 였다. **이 방향으로 가면 RLS 가 선행 조건이 된다.**
피드는 "어떤 행을 누가 볼 수 있나"를 정의해야 만들 수 있고, 그게 정확히 RLS 작업이기 때문이다.

- 먼저: **가시성 모델**(공개 / 팔로워 / 그룹 / 비공개)을 데이터로 정의
- 그 다음: RLS 를 그 모델대로 작성
- 그 위에: 피드 쿼리

**기존 데이터는 전부 "그룹 전용"으로 시작해야 한다.** 기본값이 공개면 사고다.

## v1.0.0 과의 관계 — 판단이 필요하다

이 방향 전체를 v1.0.0 에 넣는 것은 **권하지 않는다.**

- v1.0.0 은 이미 **1년치 쌓인 변경**을 내보내는 릴리스다. 여기에 제품 정체성 전환까지 얹으면
  문제가 생겼을 때 원인을 좁힐 수 없다
- 소셜 그래프는 **한 번 열면 되돌리기 어렵다** — 팔로우 관계와 공개된 게시물은 회수가 안 된다
- RLS 선행이 필요한데, 그것만으로도 테이블별로 쪼개야 하는 큰 작업이다

**제안하는 분할**:

| 릴리스 | 범위 |
|---|---|
| **v1.0.0** | 쌓인 것 + **하단 네비게이션만** — 화면 구조를 미리 잡아두면 이후 피처가 자연스럽게 들어갈 자리가 생긴다. 되돌리기도 쉽다 |
| **v1.1** | RLS 정비 + 가시성 모델 (사용자에게 안 보이는 기반 작업) |
| **v1.2** | 프로필·팔로우 |
| **v1.3** | 피드 |

네비게이션만 먼저 내보내면 **사용자가 변화를 점진적으로 겪고**, 우리는 각 단계에서 되돌릴 수 있다.

## 6. 결정이 필요한 것

각 하위 문서에도 있지만 **전체에 걸린 것**만 여기 모은다.

- [ ] **"게시물"이 새 엔티티인가?** 기존 기도카드·감사카드·말씀카드를 피드에 흘리는 것인지,
      별도 게시물 테이블을 만드는 것인지에 따라 설계가 완전히 갈린다 → [feed.md](feed.md) 1절
- [ ] **v1.0.0 범위** — 위 분할안대로 네비게이션만 넣을지, 전체를 넣을지
- [ ] **기존 사용자의 기존 데이터** — 전부 비공개(그룹 전용) 유지가 기본. 동의한다면 확정
- [ ] **기도제목을 공개할 수 있게 할 것인가** — 제품 정체성의 핵심 질문이다.
      공개하지 않는다면 피드에 흐를 것은 감사카드·말씀카드·새 게시물 종류뿐이다
